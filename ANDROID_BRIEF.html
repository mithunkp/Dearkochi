Dear Kochi Android Brief

Everything an Android client needs to talk to the same database, the same tables and the same accounts as the live Dear Kochi website. Written against the production schema as it actually is on 11 September 2026, not as the SQL files describe it.

Blocker

Do not ship an APK against this database yet

Row-level security is effectively off. firebase_migration.sql dropped every policy across twelve tables and replaced them with CREATE POLICY "Enable generic access" ON x FOR ALL USING (true). The public key can read, write and delete every row.

Verified today, unauthenticated, against a private event:

$ curl -H "apikey: $ANON_KEY" \ "$SUPABASE_URL/rest/v1/event_messages?event_id=eq.9f5d3be0-…" HTTP 200 · 312 bytes # private event, requires_approval = true # no session, no user, full chat returned

This is worse on Android than on the web. An anon key in a JavaScript bundle takes a devtools tab; an anon key in an APK takes apktool d app.apk and one grep. Publishing a mobile app against this database puts every private conversation in it one command away from anyone who installs it.

§4 explains why this cannot be fixed with policies alone — and what has to happen first. Build against it in development by all means. Do not put it on the Play Store.

Profiles and the public identity

Every account has a row in profiles, keyed by the Firebase UID. The nickname is the only thing shown to other people. It can be null on a fresh account, and the website blocks creating or joining an event until one is set — do the same.

Never display email profiles.email is selected by some queries because it is on the row, but the web client deliberately does not render it. Real names and email addresses stay private; show the nickname and flair only. See src/components/UserDisplay.tsx.
§ 4

The identity gap

This is the single most important thing in this document, and the reason §0 is a blocker rather than a note.

Firebase issues the identity. Supabase stores the data. The two have never been introduced. Supabase has no idea who the Firebase user is, so inside every Postgres policy auth.uid() evaluates to NULL, permanently.

That is why the policies were switched off rather than fixed. With auth.uid() always null, the original policies denied everything and the app did not work at all. USING (true) was the only way to make it function. It was a reasonable decision under pressure, and it is load-bearing: writing strict policies today would break the app for everybody, on web and on Android.

So the fix is not more policies. It is a bridge, in this order:

  1. Mint a Supabase-compatible JWT carrying the Firebase UID. Either Supabase’s third-party auth integration for Firebase, or a small server endpoint that verifies the Firebase ID token and signs a JWT with sub set to the UID.
  2. Send it on every request. The Android client passes that JWT as the Authorization: Bearer header instead of the anon key, so Postgres knows who is asking.
  3. Write policies against auth.jwt() ->> 'sub' rather than auth.uid(). Now they can actually match the creator_id and user_id columns.
  4. Prove it. A script that queries every table as an anonymous client and expects 401 or an empty set. Run it in CI so this cannot silently regress.
Roughly a day of work And it unblocks everything: private chats become genuinely private, the approval flow starts meaning something, and the anon key becomes safe to ship in an APK. Do it before the Play Store listing, not after.

§ 7

Realtime

All three tables are in the supabase_realtime publication, so Postgres change streams work out of the box. The web client subscribes to these channels; mirror them.

ChannelEventsFilterDo on fire
event_messages:{id}INSERTevent_id=eq.{id}Refetch the thread
event_participants:{id}*event_id=eq.{id}Refetch participants, own status, and pending requests if host
local_events_changes*none — table wideRefetch the list
Unsubscribe on teardown Tie each channel to the screen’s lifecycle and remove it in onDestroy. Supabase caps concurrent realtime connections, and leaked channels from rotated or backgrounded activities will hit that ceiling long before real traffic does.
§ 8

Rules the client must enforce

The database will not enforce any of these today, and the web client got most of them wrong before 11 September 2026. Each one is a bug that reached production, so treat this as a regression list.

RuleWhat went wrong without it
Guard submit
synchronously		 A disabled flag set after an await leaves the button live during that await. The same “Morning Run” was inserted five times in 243ms. Use a synchronous flag or mutex before any suspension point — not a state variable set later.
start_time must be
in the future		 Past events were accepted silently, so three existing events start months before they were created and have never appeared in any list.

+ chosen duration		 Scheduled events got a hard-coded start + 3h, so they vanished from the list three hours in regardless of how long they actually ran.

coordinates		 Both were hard-coded null on insert, which is why the area filter has never matched a single row and no event can be shown on a map or sorted by distance.

not event_type		 A filter keyed on event_type = 'live' lists finished events. Compute upcoming / happening / ended from start_time and end_time. Port src/lib/event-time.ts.

§ 9

Landmines

Real properties of the live data that will surprise you.

  • User IDs come in two shapes. Most are 28-character Firebase UIDs like nAxVkP5UWEZtz6S0M7hPOWtduVB3, but rows created before the migration hold Postgres UUIDs like ff72524a-2d6a-4d95-b134-f9c9d8fb9803. Those accounts cannot sign in any more, so their events and messages can never match a current user. Do not assume the column parses as a UUID, and do not assume a 28-char shape either.
  • The same is true of profiles.id, and some of those rows have a null nickname. Render a fallback rather than crashing.
  • Visibility is driven entirely by end_time. Anything with a past end_time is invisible to every list query. As of today that is all 17 events in the database.
  • There are no indexes on local_events.end_time or event_participants.event_id, which every list query hits. fix_duplicate_events.sql in the repo adds them.
  • The database holds 17 test events and 23 test messages — titles like test and kkk, fifteen messages that say “hi”. Delete them before launch rather than shipping a listing full of them.
  • is_closed exists and nothing filters on it. Decide deliberately: the web client keeps closed events visible so people who already joined keep their chat.
  • No push notifications exist anywhere. For a meet-up app this is the retention loop — someone joined, you were approved, it starts in an hour. FCM is unconfigured; budget for it as new work.
§ 10

Before you ship

Development against the current backend is fine. These are the gates for a public Play Store release.

  1. The JWT bridge from §4 is live and a script proves an anonymous client is refused by every table.
  2. Report and block are in the app. Google’s user-generated content policy requires in-app reporting and blocking before review, and a meet-up app puts strangers in rooms together.
  3. 18+ at signup. Under-18s need verifiable parental consent under the DPDP Act 2023, which is genuinely onerous. Confirm with counsel; this is not legal advice.
  4. A grievance contact is published. India’s IT Rules 2021 require a named contact, acknowledgement within 24 hours and resolution within 15 days for a platform hosting user content.
  5. Test data is gone and at least one real recurring event exists, so the first person who installs it sees something worth joining.
Recommended route If the goal is a Play Store listing quickly, wrapping the existing PWA in a Trusted Web Activity gets there in about a week from the current codebase, against a native Kotlin or Expo build of 8–16 weeks. The strategy behind that recommendation is in the companion plan.
